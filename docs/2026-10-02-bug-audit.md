# Ricotta bug audit — 2 October 2026

Scope: current GitHub `main` at `db4f345`, the connected Supabase schema,
deployed Edge Functions, recent error logs, browser requests and office launcher.
No paid feature or dependency was added.

## Verified findings and fixes

| Finding | Evidence and resulting fix |
| --- | --- |
| Repeated Rico alerts generated duplicate-key errors | Recent logs contained 230 conflicts on `app_assistant_alerts_pkey`. Atomic conflict-ignore inserts return whether this tick actually claimed the alert. Database failures now remain errors instead of being mistaken for an already-sent alert. |
| Rico inbox retries also generated duplicate-key errors | Logs contained two conflicts on the inbox deduplication key. Retry inserts now preserve one message per account without replacing the original message. |
| A crashed worker could leave a receipt or ingredient task stuck | There was no transition out of an abandoned `submitting` state. Submission claims now record their start time. Existing minute maintenance moves unresolved submissions older than 15 minutes, and unconsumed approvals older than 30 minutes, to `needs_checking`. A person reconciles them with the workplace; recovery does not retry a click or add stock. Legacy submissions without the new timestamp are also recoverable. |
| Slow stock reads could overwrite data from a newer write | Clearing the request cache did not invalidate requests already running. Reads begun before or during a write are now discarded after that write, including after account-data resets. |
| Stock responses could reach a different active UI account | Stock checked the stored token but did not recheck the displayed account after JSON decoding. Responses now check both, before and after decoding. A stale 401 cannot sign out the newer UI. |
| A late launcher acknowledgement could consume a newer start request | The server stored the acknowledgement's current time. The launcher now sends the start timestamp it actually observed, and the server updates only that matching request. Older launchers remain accepted. |
| Failed launcher acknowledgements were never retried | The launcher marked a request handled before the server accepted it. It now records success afterward and remembers which request already opened a worker window, allowing retries without duplicate windows. |
| Worker health and acknowledgement failures could look successful | Database errors were ignored on control writes and reads. They now propagate, and health-write throttling starts only after a successful write. |

## Database review

- All 32 app tables have RLS enabled. Browser roles have no table access or
  permission to create objects in `public`. All existing public RPC helpers deny
  browser-role execution. The informational [no-policy notices](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) are intentional:
  the app uses PIN-authenticated Edge Functions for access.
- The performance advisor lists [14 unused indexes](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index). None are duplicate definitions;
  these support relationships, sessions or newer workflows. Unused counters on
  this small database do not establish that an index is useless, so they were kept.
- No receipt or ingredient tasks were present during the initial live audit.
  The recovery fix addresses a reproducible failure path rather than changing an
  existing restaurant transaction.
- PostgreSQL is 17.6. Schedule a maintenance update following
  [Supabase's 17.11 guidance](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes).
  This audit did not initiate an upgrade or restart. `pgcrypto` is installed;
  `ltree` and `btree_gist` are not installed.
- One missing `image_base64` column error appeared in the logs. No repository
  code references that column; current screenshots use `image` or `shot`.
  No schema column was added to accommodate that isolated query.

## Other observations

Rico's provider logs included three Groq 413 responses, one Groq 429 response and
one slow Gemini response. These reflect rejected request sizes, provider limits
and a timeout. The app already supports provider fallback; no paid model or plan
was enabled. These upstream conditions are not claimed to be resolved by this
release.

The deployed `stock-api` and `send-push` sources matched the starting GitHub
version. The existing minute job can run recovery without adding another Edge
Function invocation schedule.

# Ricotta review — 24 October 2026

Reviewed the latest merged implementation, including Claude's navigation, Admin, iPhone, popup and animation changes. This release preserves that design and the existing shared-kitchen permissions. No restaurant orders, catalog entries, PIN values or account credentials were changed during testing.

## Fixes

| Finding | Change |
| --- | --- |
| An unsent Rico message used one browser-storage key for both accounts. | Separate draft keys per account. The old key had no reliable owner, so it is cleared rather than shown to another person. This clears only that old unsent text, not saved chats. |
| A chat opened over a slow connection could replace a newer selection or a new chat. | Track chat requests and chat lifetimes; only the current selection may populate the thread. |
| An aborted reply could finish after New Chat and reset the next reply's state. | Ignore streamed events and completion handlers from the previous chat. |
| Pending microphone permission or transcription could finish after sign-out or a chat change. | Stop microphone tracks from obsolete permission requests and discard obsolete transcriptions. Prevent overlapping microphone-start requests. |
| An AI consent popup completing during an account change could save consent to the next account. | Bind the consent decision to its original account/chat lifetime. |
| Bootstrap and Rico read only the first database page of suppliers, items and units. | Read all pages with deterministic ordering; tests include more than 1,000 of each. The current kitchen is below that boundary. |
| List sorting allocated an expensive language collator for every comparison. | Reuse one collator per language. A local 183-row sorting benchmark (20 sorts) went from 3,640 allocations / 17.64 ms to 1 allocation / 1.04 ms. This measures sorting, not overall network/load speed. |
| Overlapping PIN changes could each pass the duplicate-PIN check before either committed. | Lock the account rows in a consistent order before the check. Recheck the live admin session inside the database function. |
| Sign-in could pass its PIN check, then issue a new session after a concurrent PIN change had revoked sessions. Two concurrent accounts could also race to bind the same unused device id. | Check the PIN, complete the login reservations, issue the session and bind its device in one transaction using the same account locks as PIN changes. A failure rolls everything back. |
| The PIN changed even if its separate security-audit insert failed. | Write the audit event in the same transaction; a failed audit insert rolls the change back. Remove the redundant API-side insert and unused ID helper. |
| A sign-in service outage was shown as an incorrect PIN. | Treat timeouts and server failures as connection trouble, while retaining the wrong-PIN message for rejected credentials. |
| The native iPhone wrapper was labelled Website in the device list. | Recognize its existing native-shell flag as App. |
| Secret scanning downloaded a Linux-only executable; a UI test assumed Linux's font serialization. | Support pinned, checksum-verified macOS/Linux scanner binaries and equivalent system-font serialization. |
| A native navigation comment still claimed no bridge existed. | Correct the comment to describe the existing restricted haptic/appearance bridge. |

## Security and database checks

- All 24 public app tables have RLS enabled; anonymous and authenticated browser roles have no table access. All public internal functions deny execution to those roles. The no-policy advisor notices are informational and intentional for this server-only access model.
- Both PIN hashes use bcrypt cost 12. Session tokens are random; only token hashes are stored. No active sessions were bound to a missing/wrong-account device in the live check.
- API health answered successfully. Unauthenticated bootstrap returned 401, a foreign Origin returned 403, and the push worker without its private cron secret returned 403. API responses include no-store, restricted CORS, CSP, HSTS, nosniff, no-referrer and frame-denial headers. Cloudflare sign-in verification is enabled.
- The live API and push source matched the latest repository source before this work, apart from trailing whitespace. Live migrations matched the repository's latest functional changes.
- The four scheduled jobs remain enabled; no cron failures were recorded in the preceding 24 hours. No invalid stored order quantities were found.
- Redacted Gitleaks scans covered all fetched Git refs (257 commits before this release) and current files. No unignored findings. The development dependency audit and all 32 locked runtime npm packages had no known advisories at review time.
- Existing tests exercise request-size limits, invalid JSON, push endpoint restrictions, provider quotas, authorization, XSS escaping, formula-safe exports, monthly retention, draft conflicts and offline order retries. New regressions cover the fixes above.
- The publishing build remains an allowlist: database/function sources, migrations, private exports, environment files, tests and dependency directories are excluded from the website.

## Deliberately retained

The unfinished Transfers feature is intentionally locked by the latest implementation. Its code and empty stock table are development work, not proven unused code to delete. The three advisor-reported unused indexes were retained: they support account relationships/history queries, and recent usage statistics alone do not justify dropping them. Development dependencies all serve builds, linting or tests.

## Remaining limitations and ideas

This is a code, regression and live-configuration review, not proof that every vulnerability is absent. A six-digit account PIN and an 18-hour bearer session remain weaker than individual accounts with stronger authentication. Session storage remains accessible to same-origin JavaScript, making the strict CSP and escaped rendering essential. GitHub Pages cannot provide custom frontend response headers such as frame-ancestors and Permissions-Policy; that requires a hosting/proxy change. Native camera/microphone prompts and WhatsApp handoff still benefit from real-iPhone checks; mocked UI tests cannot establish those end-to-end behaviors. No paid services, forced credential rotations or backup schedule were introduced.

Useful next additions that keep the interface small:

1. A compact connection/sync explanation only when something needs attention: offline, pending order save, or a draft conflict.
2. A duplicate-item review inside Manage that shows likely matches and asks before merging anything.
3. A lightweight owner-only diagnostics page for API status, failed scheduled jobs and pending saves, rather than adding more everyday tabs.

Backups remain disabled at the owner's request. Without a current verified backup, accidental or malicious data loss remains a recovery risk.
